# unifi_monitoring

Ставит на self-hosted контроллер UniFi один скрипт и один `UserParameter`, чтобы уже
работающий там агент Zabbix отдавал всю опись устройств контроллера в виде JSON.

Выполняется **на хосте контроллера**, после `zabbix_agent`.

## Почему не опрос устройств и почему не API

Точки доступа и коммутаторы UniFi не отвечают по SNMP вообще. Ubiquiti убрала настройку из
UniFi Network — в 10.4.57 её нет, — а поскольку конфигурацию устройства целиком получают от
контроллера, включённый на каждом вручную `snmpd` перезаписывается при следующей провизии.
Проверено пробой: они молчат на 161 даже из своего же L2.

Собственный API контроллера работает, но аутентифицирует **локального** администратора, и
учётная запись Ubiquiti SSO его не заменяет: она отвечает `api.err.Ubic2faTokenRequired`, а
удовлетворить двухфакторную аутентификацию в автоматическом опросе нечем. В итоге
развёртывание упирается в ручной шаг в веб-интерфейсе.

У базы, на которой работает контроллер, такого требования нет. Она слушает
`127.0.0.1:27117` без аутентификации, поэтому выполнение запроса **на хосте контроллера** и
есть вся авторизация — отсюда роль для этого хоста, а не HTTP-шаблон.

## Что даёт и чего не даёт

Из `ace.device`: имя, адрес, MAC, модель, тип, версия прошивки, требуемая версия, серийный
номер, adopted, internet, unsupported, снятие с поддержки, `last_seen`, `connected_at`,
`disconnected_at`, `provisioned_at`.

**Живой телеметрии нет**: CPU, память, аптайм в понимании самого устройства и число
клиентов в базу не пишутся вовсе. Они существуют только в памяти контроллера и выходят
наружу через API. Если они нужны — заведите локальную учётку и берите
`UniFi Device by HTTP`; оба шаблона уживаются вместе.

Состояние подключения тоже не хранится, а выводится. Контроллер держит две отметки времени,
из которых оно следует, и побеждает более поздняя: у переподключившегося после обрыва
устройства `connected_at` новее, чем `disconnected_at`.

## Ловушка, которую стоит знать

`mongosh` — программа на Node. Она переходит в рабочий каталог и хочет писать в `HOME`, а
агент Zabbix работает от системного пользователя, которому может быть нельзя ни то ни
другое. Тогда node умирает с `EACCES` ещё до первого запроса. Скрипт задаёт обе переменные
сам, а не наследует то, что было у вызывающего: успешная проверка команды под root ничего
не говорит об агенте — поэтому `unifi_monitoring_verify` запускает готовый скрипт **от
пользователя агента**.

## Переменные

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `unifi_monitoring_mongosh_path` | `/usr/bin/mongosh` | Поставляется с пакетом контроллера |
| `unifi_monitoring_mongo_port` | `27117` | Порт встроенной MongoDB, только loopback |
| `unifi_monitoring_mongo_database` | `ace` | Где контроллер держит опись |
| `unifi_monitoring_script_path` | `/usr/local/bin/unifi_facts.sh` | Скрипт сбора |
| `unifi_monitoring_userparameter_path` | `/etc/zabbix/zabbix_agent2.d/20-unifi.conf` | Номер после drop-in роли `zabbix_agent` |
| `unifi_monitoring_item_key` | `unifi.devices` | Обязан совпадать с мастер-элементом шаблона |
| `unifi_monitoring_agent_user` | `zabbix` | От кого выполняется проверка |
| `unifi_monitoring_verify` | `true` | Проверять, что пользователь агента реально получает данные |

## Шаблон, который это потребляет

`UniFi devices by controller DB`, лежит в `files/` роли `zabbix_server` и импортируется из
Git, как и любой другой собственный шаблон. Один агентский элемент возвращает всю опись,
зависимое правило обнаружения создаёт элементы по устройствам — один запрос к базе за
интервал покрывает парк любого размера.

Привязывать его нужно к **хосту контроллера**, а не к устройствам. Устройства остаются
отдельными хостами с `ICMP Ping`: достижимость относится к собственному адресу устройства,
а всё прочее — это то, что знает о нём контроллер.
